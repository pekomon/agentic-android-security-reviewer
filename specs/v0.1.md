# v0.1 — Android Manifest Security Review

## Goal

Build a focused AI agent that analyzes an Android application's
`AndroidManifest.xml` and produces structured, evidence-based security findings.

The purpose of v0.1 is to establish a small but production-oriented agent
workflow that separates deterministic fact extraction from probabilistic
security reasoning.

## Scope

The agent analyzes security-relevant configuration available directly from
`AndroidManifest.xml`.

Supported manifest facts and review areas include:

- exported Android components
- component permissions
- application debuggability
- cleartext traffic configuration
- application backup configuration
- requested permissions
- intent filters
- deep-link data constraints

The scope is intentionally limited to evidence available from the manifest.

## Architecture

The review workflow separates deterministic parsing from model-dependent
security reasoning:

```text
AndroidManifest.xml
        ↓
Security Review Agent
        ↓
MCP tool: inspect_manifest
        ↓
Android Security MCP Server
        ↓
deterministic manifest parser
        ↓
structured ManifestFacts
        ↓
Security Review Agent
        ↓
structured SecurityReview
```

The MCP server exposes deterministic manifest inspection as a reusable
capability. The agent must use the structured facts returned by the tool rather
than independently interpreting the XML.

## Requirements

### Evidence-based findings

Every security finding must be supported by facts produced by the manifest
inspection tool.

The agent must not invent configuration, components, permissions, application
data, deployment context, or security impact that is not supported by the
available evidence.

### Deterministic fact extraction

Facts that can be extracted reliably from the manifest must be produced by
deterministic code rather than inferred by the language model.

Unknown or unavailable facts should remain explicit instead of being converted
into assumptions.

### Uncertainty

If the available facts do not contain enough information to determine whether
something is a confirmed vulnerability, the agent must communicate the
uncertainty and classify the issue appropriately.

For example, configuration such as `android:debuggable="true"` or
`android:allowBackup="true"` may require security review without proving a
production vulnerability by itself.

### Structured output

Each finding contains:

- category
- severity
- classification
- title
- description
- evidence
- recommendation
- confidence

A review contains a structured list of findings. If no supported
security-relevant findings exist, the list should be empty.

### Security reasoning

The agent should distinguish between:

- confirmed vulnerabilities
- potential risks that require additional context
- normal or secure configuration that should not produce a finding

The agent should avoid noisy findings for ordinary permissions or unsupported
configuration.

### Tool use

The agent must use the `inspect_manifest` MCP tool before producing security
analysis.

The same tool should also be usable independently by other MCP-compatible
clients.

## Testing and evaluation

Deterministic behavior is covered by automated tests.

These tests verify:

- manifest fact extraction
- handling of missing facts
- component and permission parsing
- intent-filter and deep-link parsing
- MCP server discovery and structured tool output

Model-dependent behavior is covered by agent evals.

Eval cases include both positive and negative examples, such as:

- clean manifests
- debug configuration
- cleartext traffic
- exported components
- ordinary permissions that should not create findings
- broad package visibility
- browsable deep links
- application backup configuration

A separate tool-use eval verifies that the agent actually calls
`inspect_manifest`.

## Observability

Agent workflows are traced so that model calls, MCP tool calls, tool outputs,
and final structured findings can be inspected.

Tracing should make it possible to distinguish failures in:

- deterministic fact extraction
- agent policy or reasoning
- workflow orchestration and tool use

## Out of scope for v0.1

The following are intentionally excluded:

- application source code analysis
- dependency vulnerability analysis
- APK decompilation
- runtime behavior analysis
- network traffic inspection
- external vulnerability databases
- automatic remediation
- multi-agent orchestration
- sandbox execution
- multi-provider model support

## Success criteria

v0.1 is successful when:

1. An Android manifest can be provided to the review agent.
2. The agent obtains manifest facts through `inspect_manifest`.
3. Deterministic manifest facts are returned as structured data.
4. The agent produces structured security findings based on those facts.
5. Every reported finding is traceable to supplied evidence.
6. The agent communicates uncertainty instead of overclassifying incomplete
   evidence.
7. Secure or ordinary configuration does not create unnecessary findings.
8. Deterministic behavior is protected by automated tests.
9. Model-dependent behavior is exercised by agent evals.
10. Tool use is explicitly verified.
11. The MCP inspection capability can be consumed independently by an external
    MCP client.
